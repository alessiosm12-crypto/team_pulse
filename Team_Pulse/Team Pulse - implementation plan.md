# Team Pulse / Пульс команд: план реализации MVP

## 1. Цель документа

Этот документ фиксирует пошаговый план реализации Team Pulse от текущей продуктовой идеи до работающего MVP и пилота на проектных командах.

Базовое допущение: первая версия продукта создается как внутренний инструмент для HRBP, РП / Delivery Manager и руководителя направления. Цель MVP - проверить ценность короткой AI-диагностики состояния проектной команды до разработки полноценной платформы.

## 2. Цель MVP

MVP Team Pulse должен позволять:

1. Запустить короткий пульс-опрос для проектной команды.
2. Собрать ответы участников через Telegram-бота или простую форму.
3. Сохранить закрытые и открытые ответы.
4. Сформировать AI-анализ состояния команды.
5. Подготовить отчет для HRBP и руководителя.
6. Зафиксировать управленческие действия после разбора.
7. Провести follow-up через 8-11 недель.

Главная проверяемая гипотеза: короткий регулярный опрос с AI-анализом помогает HRBP и руководителю раньше увидеть командные риски и быстрее перейти к конкретным действиям.

## 3. Ключевые продуктовые решения

### 3.1. Формирование отчетов

Отчеты формируются при любом количестве ответов.

Это означает, что система не блокирует генерацию отчета для малых команд или неполного response rate. При этом в коммуникации запуска нужно явно предупредить участников, кто увидит отчет и как будут использоваться ответы.

### 3.2. Открытые комментарии

Открытые комментарии включаются в отчет дословно, без переформулирования и скрытия цитат.

Следствие: в тексте перед началом опроса обязательно нужно указать, что свободные ответы могут быть показаны в отчете как есть.

### 3.3. Роль AI

AI формирует аналитический черновик, а не окончательный управленческий вывод.

AI должен:

- обобщать оценки;
- выявлять повторяющиеся темы;
- выделять сильные стороны;
- находить зоны риска;
- предлагать гипотезы причин;
- формировать рекомендации для HRBP и руководителя.

AI не должен:

- ставить психологические диагнозы;
- делать выводы о конкретных людях;
- обвинять руководителя или команду;
- выдавать рекомендации как обязательное решение;
- скрывать риск низкой надежности вывода при малом количестве ответов.

### 3.4. Human-in-the-loop

Рекомендуемый режим MVP: отчет сначала видит HRBP, затем HRBP решает, как использовать его с руководителем.

В первой версии не стоит автоматически отправлять AI-отчет руководителю без просмотра HRBP.

## 4. Пользователи и роли

### Респонденты

Участники проектной команды: разработчики, аналитики, тестировщики, дизайнеры, тимлиды и другие роли.

Их цель: безопасно дать обратную связь о состоянии команды, нагрузке, коммуникации, препятствиях и рисках.

### HRBP / People Partner

Основной пользователь аналитики.

Его задачи:

- быстро увидеть состояние команды;
- понять, куда смотреть глубже;
- подготовиться к разговору с РП;
- выбрать формат интервенции;
- отслеживать изменения после действий.

### РП / Delivery Manager / Team Lead

Пользователь управленческого отчета.

Его задачи:

- понять, что происходит внутри команды;
- увидеть зоны риска;
- получить вопросы для обсуждения;
- выбрать 1-2 действия на ближайшие 2-4 недели.

### Руководитель направления

Спонсор или заказчик пилота.

Его задачи:

- видеть, какие команды находятся в зоне риска;
- снижать вероятность delivery-срывов;
- снижать риск потери ключевых людей;
- управлять устойчивостью команд на уровне портфеля.

## 5. Объем MVP

### Входит в MVP

- создание опроса для команды;
- прохождение опроса;
- закрытые вопросы по шкале 1-5;
- открытые вопросы;
- сохранение ответов;
- запуск AI-анализа;
- отчет для HRBP;
- отчет для руководителя;
- фиксация action items;
- повторный замер через 8-11 недель.

### Не входит в MVP

- полноценная админ-панель;
- сложная ролевая модель;
- интеграции с HRIS, Jira, Slack, Teams;
- автоматический портфельный дашборд;
- историческая аналитика по всем командам;
- автоматические рекомендации без проверки HRBP;
- внешняя SaaS-монетизация.

## 6. Диагностическая модель

Опрос должен покрывать следующие блоки:

1. Цели и фокус.
2. Роли и ответственность.
3. Нагрузка и устойчивость.
4. Коммуникация и взаимодействие.
5. Психологическая безопасность.
6. Управление и поддержка со стороны РП / руководителя.
7. Процессы и препятствия.
8. Delivery-риски.

Для MVP достаточно 10-12 закрытых вопросов и 2-3 открытых вопроса.

## 7. Scoring-модель

### Зеленая зона

- Большинство блоков оцениваются на 4.0+.
- Нет повторяющихся критичных комментариев.
- Нет резких расхождений между оценками.
- Команда видит проблемы, но способна обсуждать и решать их.

### Желтая зона

- Один или два блока ниже 3.5.
- Есть повторяющиеся темы напряжения.
- Есть признаки перегруза, неясности ролей, разрыва ожиданий или коммуникационных сложностей.
- Требуется управленческое внимание в ближайшие 2-4 недели.

### Красная зона

- Один или несколько критичных блоков ниже 3.0.
- Есть сигналы конфликта, выгорания, недоверия, риска ухода или delivery-срыва.
- Команда может избегать открытого обсуждения проблем.
- Нужна интервенция HRBP и руководителя.

Важное правило: при малом количестве ответов система все равно формирует отчет, но должна помечать выводы как менее надежные.

## 8. Архитектура MVP

Рекомендуемая простая архитектура:

```text
Telegram Bot / Web Form
        |
Backend API
        |
Database
        |
AI Analysis Service
        |
Report Generator
        |
HRBP / Manager Reports
```

Рекомендуемый стек:

- Backend: Python FastAPI или Node.js / NestJS.
- Bot: Telegram Bot API.
- Database: PostgreSQL.
- AI: OpenAI API.
- Reports: Markdown / HTML, позднее PDF.
- Admin UI: на первом этапе минимальный интерфейс или ручной запуск анализа.

## 9. Основные сущности данных

Минимальная модель:

- `Team` - проектная команда.
- `Survey` - конкретный запуск опроса.
- `Question` - вопрос и его диагностический блок.
- `Response` - ответ участника.
- `AIAnalysis` - результат AI-анализа.
- `Report` - отчет для HRBP или руководителя.
- `ActionItem` - управленческое действие после разбора.
- `FollowUp` - повторная проверка состояния.

Что важно хранить:

- версия набора вопросов;
- версия AI-промпта;
- дата запуска опроса;
- дата закрытия опроса;
- количество ответов;
- средние оценки по блокам;
- исходные открытые комментарии;
- итоговый статус команды;
- принятые действия.

## 10. Сценарий пользователя

### Сценарий HRBP

1. HRBP выбирает команду.
2. Создает новый пульс-опрос.
3. Передает участникам ссылку или приглашение в Telegram-бота.
4. Дожидается ответов.
5. Запускает AI-анализ.
6. Проверяет отчет.
7. Обсуждает отчет с РП.
8. Фиксирует 1-2 действия.
9. Планирует follow-up.

### Сценарий участника команды

1. Получает приглашение пройти короткий опрос.
2. Видит объяснение цели, правил обработки данных и использования цитат.
3. Отвечает на закрытые вопросы.
4. Пишет открытые комментарии.
5. Завершает опрос.

### Сценарий РП

1. Получает отчет от HRBP.
2. Видит общий статус команды.
3. Изучает сильные стороны и зоны риска.
4. Обсуждает выводы с HRBP.
5. Выбирает действия для команды.
6. Возвращается к результатам на follow-up.

## 11. План реализации

### Этап 1. Продуктовая фиксация

Срок: 1-2 дня.

Результаты:

- утвержден MVP;
- утверждены роли пользователей;
- утверждены правила отчетности;
- утвержден текст про использование дословных цитат;
- утверждены критерии успеха пилота.

### Этап 2. Методология опроса

Срок: 2-3 дня.

Результаты:

- финальный список вопросов;
- диагностические блоки;
- scoring-модель;
- правила интерпретации;
- шаблон отчета.

### Этап 3. AI-прототип анализа

Срок: 2-3 дня.

Результаты:

- системный промпт AI-аналитика;
- JSON-схема результата;
- тестовые наборы синтетических ответов;
- 3-5 пробных отчетов;
- список ограничений и edge cases.

### Этап 4. Технический MVP

Срок: 5-7 дней.

Результаты:

- Telegram-бот или простая форма;
- backend API;
- база данных;
- сохранение ответов;
- запуск AI-анализа;
- генерация отчета в Markdown / HTML;
- минимальный ручной сценарий для HRBP.

### Этап 5. Внутренний тест

Срок: 2-3 дня.

Результаты:

- тестовый опрос на небольшой группе;
- проверка UX;
- проверка сохранения данных;
- проверка AI-анализа;
- корректировка промпта;
- корректировка вопросов.

### Этап 6. Пилот

Срок: 2-4 недели.

Результаты:

- запуск на 2-3 командах;
- сбор ответов;
- формирование отчетов;
- встречи HRBP + РП;
- фиксация действий;
- оценка полезности отчета;
- подготовка выводов по пилоту.

### Этап 7. Follow-up

Срок: через 8-11 недель после первого замера.

Результаты:

- повторный пульс;
- сравнение состояния команды;
- проверка выполненных действий;
- решение о масштабировании продукта.

## 13. Метрики успеха пилота

Метрики запуска:

- 2-3 команды в пилоте;
- response rate 60-70%+;
- среднее время заполнения до 7 минут;
- завершение опроса 85%+ начавших.

Метрики качества отчета:

- оценка полезности отчета РП 4/5+;
- оценка полезности отчета HRBP 4/5+;
- доля выводов, признанных точными, 70%+;
- доля рекомендаций, пригодных для действия, 70%+.

Метрики управленческого действия:

- 100% команд провели разбор после отчета;
- 50%+ команд приняли хотя бы одно действие;
- выявлен хотя бы один риск до эскалации;
- follow-up показывает выполнение действий или изменение состояния команды.

Метрики доверия:

- участникам понятны правила использования ответов;
- нет жалоб на неожиданное использование дословных комментариев;
- открытые ответы содержательны, а не формальны.

## 14. Риски и меры управления

### Риск деанонимизации

Так как отчеты формируются при любом количестве ответов и цитаты показываются дословно, участники могут быть узнаваемы по стилю или содержанию комментария.

Меры:

- явно предупредить об этом до начала опроса;
- указать, кто увидит отчет;
- не обещать полную анонимность там, где она фактически невозможна;
- использовать формулировку "ответы используются в отчете команды", а не "никто не сможет понять автора".

### Риск неверной интерпретации AI

AI может переоценить единичный комментарий или не понять контекст.

Меры:

- HRBP проверяет отчет;
- AI указывает степень уверенности;
- отчет отделяет факты, наблюдения и гипотезы;
- рекомендации формулируются как варианты действий.

### Риск защитной реакции руководителя

РП может воспринять отчет как оценку его работы.

Меры:

- позиционировать отчет как инструмент улучшения условий работы команды;
- начинать с сильных сторон;
- давать конкретные вопросы для обсуждения;
- избегать обвинительных формулировок.

### Риск низкого response rate

Малое количество ответов снижает надежность выводов.

Меры:

- показывать количество ответов;
- помечать выводы как предварительные;
- использовать follow-up;
- улучшать коммуникацию запуска.

## 15. Использование AI-инструментов при разработке

### Product discovery

AI используется для:

- уточнения Lean Canvas;
- подготовки вопросов для интервью;
- генерации гипотез пилота;
- описания CJM;
- создания PRD.

### Методология

AI используется для:

- генерации и редактирования вопросов;
- проверки нейтральности формулировок;
- группировки вопросов по блокам;
- подготовки scoring-модели;
- создания шаблонов отчетов.

### Разработка

AI-coding инструменты используются для:

- генерации структуры backend;
- создания Telegram-бота;
- проектирования схемы базы;
- написания API;
- генерации тестов;
- подготовки документации.

### Качество и безопасность

AI используется для:

- code review;
- поиска privacy-рисков;
- генерации edge cases;
- проверки промптов;
- анализа тестовых отчетов.
